# AGENTS.md — WolvenKit native Linux port

Shared rules for every agent (Claude Code, OpenAI Codex) working in this fork.
Fork: `LaAutista/WolvenKit` · Upstream: `WolvenKit/WolvenKit` · License: GPL-3.0 (keep it, keep attribution).

## Goal

A native Linux build of WolvenKit (Arch Linux / CachyOS first), GUI included, X11 and Wayland.
No Wine/Proton for WolvenKit itself. Proton is only how the *game* runs.

## Coordination rules

1. Work only in your own worktree and on your own `linux/<agent>/…` branches. Never edit the other agent's worktree.
2. Every task in `PORT_PLAN.md` has one owner. To take or hand over a task, change the owner there and say so in the issue.
3. Integrate through pull requests into `linux/main` on the fork. The *other* agent reviews; merge only after its approval or after its findings are fixed. Disagreements are settled with tests or measurements, not opinion.
4. Never force-push `linux/main` or a branch the other agent has based work on. Never push to `upstream`. Do not open PRs or issues on `WolvenKit/WolvenKit` without the user's explicit go-ahead.
5. After each working session update `AGENT_HANDOFF.md` (branch, commit hashes, what is verified, what is open) and post a short note in the coordination issue.
6. Report only what actually ran. Paste the command and its result. "Builds" is not "works".
7. Do not install system packages or change the user's environment (`pacman`, `sudo`, global dotnet tools, shell config) — ask the user. User-local build output and NuGet caches are fine.
8. Never write inside a game directory, a Proton prefix, or a user's mod project during tests. Read game archives read-only; write test output to a temp directory.
9. Do not commit proprietary game assets. Test fixtures must be generated by the tests or be redistributable.

## Engineering rules

- Keep the diff against upstream small so upstream merges stay cheap: prefer additive files and new projects over editing shared code; when shared code must change, make the change platform-neutral and upstreamable, and keep Windows behaviour identical.
- Reuse the existing C# libraries (`WolvenKit.Core`, `.RED4`, `.Common`, `.Modkit`) and view models. Do not rewrite mature logic.
- Linux-only code lives in new projects/files (`WolvenKit.Linux*`, `*.Linux.cs`) or behind `OperatingSystem.IsLinux()`.
- Paths: use `Path.Combine`/`Path.DirectorySeparatorChar`, never hard-coded `\\`. Assume case-sensitive filesystems; resolve game paths case-insensitively where the game does.
- Follow upstream conventions (`docs/CONTRIBUTING.md`, `.editorconfig`). Small focused commits, imperative subject lines.
- New logic ships with a test. Linux tests run with `dotnet test` on plain `net10.0` (no Windows TFM).
- Toolchain: .NET SDK 10 (`global.json`). On the dev machine it is at `~/.local/share/recovery-toolchain/bin/dotnet`.

## Build quick reference

```bash
dotnet build WolvenKit.CLI/WolvenKit.CLI.csproj      # verified on CachyOS, 2026-11-15
```

More commands are added to `docs/linux/PORT_PLAN.md` as they are verified.
